# Бот и MCP-сервер для группы MeshTRX

Даёт агенту читать переписку группы в Telegram и отвечать в неё, а участникам —
задавать вопросы по документации командой `/ask`.

## Устройство

```
        сервер 195.133.1.248 (там же, где сайт)
        ┌──────────────────────────────────────────────┐
Telegram ┼─длинный опрос─▶ daemon.py ──▶ SQLite ◀── mcp_server.py ─┼─stdio по ssh─▶ агент
        │                    ▲             │                       │
        │                    └─ отправка ──┘                       │
        │  GitHub ──git pull──▶ /opt/meshtrx/repo (код и документация)
        └──────────────────────────────────────────────┘
```

**Почему на сервере.** Демон должен работать круглосуточно: Telegram хранит
непрочитанные обновления сутки, и при запуске «вместе с сессией» отпуск или
несколько занятых дней означали бы потерянные сообщения. Сервер сайта работает
всегда, и это ровно та машина, которая уже есть.

С сессией Claude Code сервис не связан никак: он предъявляет Telegram только
токен бота и ничего не знает про авторизацию Anthropic. По сессии живёт другой
процесс — MCP-сервер: его запускает Claude Code по `.mcp.json` командой `ssh`,
общение идёт по stdio через это соединение.

**Почему через базу, а не напрямую.** Длинный опрос Telegram отдаёт каждое
обновление ровно одному клиенту. Если бы MCP-сервер тоже ходил в сеть, два
процесса начали бы отбирать сообщения друг у друга, и часть переписки терялась
бы молча. Поэтому с Telegram говорит только демон, а всё остальное общается с
ним через базу — `/opt/meshtrx/.local/share/meshtrx/telegram.db` на сервере.

Побочная польза: отправка переживает перезапуск сессии и самого демона —
сообщение лежит в очереди, пока его не заберут.

| Файл | Ответственность |
|------|-----------------|
| `daemon.py` | единственный, кто говорит с Telegram: приём, отправка, команды |
| `mcp_server.py` | инструменты для агента поверх той же базы |
| `store.py` | схема и доступ к базе |
| `docs_index.py` | поиск по документации проекта для быстрых ответов |
| `persona.md` | как писать в группу: тон, чего не делать, примеры |
| `pick_telegram_route.py` | ищет адрес Telegram, до которого с сервера есть связь |
| `ensure_daemon.sh` | проверка из хука сессии, что сервис на сервере жив |
| `meshtrx-tgbot.service` | юнит systemd |

## Настройка

Токен лежит **вне репозитория**: репозиторий публичный, а токен даёт полный
доступ к боту. На сервере это

```
/opt/meshtrx/.config/meshtrx/telegram.env      (владелец meshtrx, права 600)

MESHTRX_TG_BOT_TOKEN=…
MESHTRX_TG_CHAT_ID=-100…                       # можно несколько через запятую
```

Локально — тот же файл в `~/.config/meshtrx/`.

Идентификатор группы отрицательный (у супергрупп начинается с `-100`).
Положительное число — это личный чат с ботом. Узнать нужный:

```bash
tools/tgbot/daemon.py --chats       # напишите что-нибудь в группе
```

Команда печатает все чаты, из которых приходят сообщения, и их идентификаторы.
Пока `MESHTRX_TG_CHAT_ID` пуст, демон принимает сообщения отовсюду, а
`telegram_send` отвечает в тот чат, откуда пришло последнее сообщение.

## Где что лежит на сервере

| Путь | Что это |
|------|---------|
| `/opt/meshtrx/repo` | клон репозитория: код бота и документация для `/ask` |
| `/opt/meshtrx/venv` | окружение Python (`httpx`, `mcp`) |
| `/opt/meshtrx/.config/meshtrx/telegram.env` | токен и список чатов |
| `/opt/meshtrx/.local/share/meshtrx/telegram.db` | переписка, очередь, вопросы |
| `/etc/systemd/system/meshtrx-tgbot.service` | сервис |

Всё под отдельным пользователем `meshtrx`, а не под root: сервису нужны только
свой каталог и сеть.

**Документация не выгружается на сервер.** Клон обновляется сам — при каждом
старте сервиса и раз в четверть часа на ходу. Запушили правку в `master` —
через пятнадцать минут бот отвечает по ней; нужно немедленно — `/reload` в
группе или `telegram_docs_reload` у агента. Так исключён случай, когда копия
на сервере отстала, а заметно это только по неверному ответу человеку.

## Запуск

Сервис работает на сервере, где хостится сайт:

```bash
systemctl status meshtrx-tgbot          # состояние
journalctl -u meshtrx-tgbot -f          # журнал
systemctl restart meshtrx-tgbot         # после правок, если ждать 15 минут не хочется
```

Хук `SessionStart` из `.claude/settings.json` при открытии проекта вызывает
`ensure_daemon.sh`: тот проверяет сервис по ssh и поднимает его, если лежит.

**Демон работает один.** Он берёт блокировку файла `daemon.lock`, и второй
экземпляр сразу выходит. Иначе два процесса начинают отбирать обновления друг
у друга: Telegram отдаёт каждое ровно одному клиенту, второму отвечает
`Conflict`, и часть переписки теряется молча. По этой же причине локальный
запуск (`ensure_daemon.sh --local`, для отладки) нельзя держать одновременно с
сервисом на сервере.

MCP-сервер запускать не нужно: его поднимает Claude Code по `.mcp.json`
командой `ssh` и общается с ним по stdio через это соединение.

### Путь до Telegram

Сервер стоит в России, и связь с Telegram оттуда неполная: имя
`api.telegram.org` резолвится в IPv6, до которого связи нет, а из известных
адресов IPv4 отвечает не каждый — на момент настройки один из шести.

Поэтому перед стартом демона `pick_telegram_route.py` перебирает адреса,
проверяя не пинг, а установку TLS-сессии, и закрепляет живой в `/etc/hosts`.
Соединение при этом идёт по имени, проверка сертификата обычная — подменяется
только разрешение имени в адрес.

Если путь пропадёт на ходу, демон досчитает двадцать сетевых ошибок подряд и
выйдет с кодом 75; systemd поднимет его снова, и маршрут переберётся. Молча
«сломанным» бот не останется.

## Инструменты агента

| Инструмент | Что делает |
|------------|------------|
| `telegram_read` | сообщения группы; по умолчанию только новые и помечает прочитанными |
| `telegram_send` | отправить в группу (через очередь), можно ответом на сообщение |
| `telegram_questions` | вопросы `/ask`, на которые ещё нет ответа |
| `telegram_answer` | ответить на такой вопрос и закрыть его |
| `telegram_status` | сколько сообщений, что не отправлено, состояние индекса |
| `telegram_docs_search` | поиск по документации — тот же, что у бота |
| `telegram_docs_reload` | пересобрать индекс после правок в репозитории |
| `telegram_style` | правила тона из `persona.md` — прочитать перед первым сообщением |

## Команды бота

- `/ask вопрос` — ищет ответ в документации. Нашёл — отвечает сразу; не нашёл —
  оставляет вопрос в очереди, и на него отвечает агент через `telegram_answer`.
- `/status` — сколько файлов в индексе, когда обновлён, сколько вопросов ждёт.
- `/reload` — пересобрать индекс.

## Тон сообщений

Правила лежат в `persona.md` — отдельным файлом, потому что их правят чаще,
чем код, и правит обычно не программист. Коротко: пишем как участник команды,
не подписываемся ботом, не разводим канцелярит. Правила действуют и для
ответов бота на команды, и для сообщений, которые агент отправляет через
`telegram_send`; агенту их отдаёт инструмент `telegram_style`.

Одно исключение из «не объявлять себя программой»: если человек прямо
спрашивает, кто отвечает, — отвечаем честно. В группе люди по этим ответам
чинят свои устройства, и доверие дороже иллюзии живого собеседника.

Поиск намеренно простой: совпадение слов с тройным весом заголовка, без
моделей и векторов. Документации в проекте десяток файлов, и на вопрос «сколько
можно говорить» такой поиск отдаёт нужный раздел руководства мгновенно. Там,
где он не справляется, вопрос уходит агенту — это честнее, чем выдавать
похожий по словам, но неверный по смыслу кусок.
