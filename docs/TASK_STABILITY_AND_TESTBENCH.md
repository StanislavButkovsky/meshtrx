# Задача: восстановление стабильности связи + постоянный тестовый стенд

> Статус: ПЛАН (составлен 2026-08-18)
> Приоритет: КРИТИЧЕСКИЙ — сейчас система неработоспособна: BLE рвётся, устройство циклически перезагружается
> Область: firmware (V3/V4) + Android. iOS отложен.

---

## 0. Краткий диагноз

Регрессия внесена последним коммитом `52d42e4` (14.05.2026, «Deploy: rebuild firmware V3/V4»).
В нём **auto light sleep был заменён на цикл deep sleep**, и это ломает связь по построению:

```
Телефон отвалился на 1 секунду (или просто не успел подключиться)
        ↓
loraTask видит !bleConnected  →  enterDeepSleep()   (main.cpp:466)
        ↓
esp_deep_sleep_start()  — это НЕ сон, это выключение с последующим ПЕРЕЗАГРУЗКОЙ
        ↓
через 10 с — полный boot (~1.5-2 с): NVS, LoRa, Codec2, NimBLE
        ↓
окно на подключение телефона = 3 секунды  (BLE_WAKE_SEARCH_MS, main.cpp:182)
    при этом advertising interval = 1000-2000 мс (ble_service.cpp:88)
    → за окно уходит 2-3 рекламных пакета, scan response выключен
        ↓
телефон не успел → enterDeepSleep() снова → бесконечный цикл ребутов
        ↓
Android: 10 попыток реконнекта (3,5,7,10,10... с) → «Нет связи» и БОЛЬШЕ НЕ ПРОБУЕТ
        (MeshTRXService.kt:198-217)
```

Внешние симптомы ровно те, что наблюдались: устройство «не просыпается» (OLED гасится при
boot из deep sleep, main.cpp:252-256), телефон теряет BLE и не восстанавливает соединение,
устройство «периодически ресетится» (это и есть deep sleep — каждое пробуждение = reset).

Второй пласт проблем (существовал и раньше, проявляется как случайные разрывы и зависания):
доступ к радио и к BLE-нотификациям идёт **из четырёх задач на двух ядрах без синхронизации**,
а тяжёлые операции LoRa-передачи выполняются **прямо внутри BLE-колбэка**, блокируя стек NimBLE.

Энергопотребление: после этого коммита `esp_pm_configure()` удалён совсем — то есть при
подключённом телефоне никакого энергосбережения нет вообще (~100 мА), а вся «экономия»
работает только когда телефона нет, ценой полной неработоспособности связи.

## 1. Карта системы (как оно работает по коду)

### 1.1 Топология

```
┌─────────────┐   BLE NUS    ┌──────────────┐   LoRa 868 МГц   ┌──────────────┐   BLE   ┌────────┐
│ Android app │◄────────────►│ Heltec V3/V4 │◄────────────────►│ Heltec V3/V4 │◄───────►│ Phone  │
│  (Kotlin)   │  40+ команд  │  ESP32-S3    │  SF7/BW250/CR4-7 │              │         │        │
└─────────────┘              │  + SX1262    │  23 канала EU868 └──────────────┘         └────────┘
                             └──────────────┘
```

### 1.2 Firmware — задачи FreeRTOS (нормальный режим)

| Задача | Ядро | Приоритет | Стек | Роль |
|--------|------|-----------|------|------|
| `loraTask` (main.cpp:425) | 0 | 5 | 16 K | RX-обработчик (DIO1 ISR → notify), TX из очередей аудио/текста, управление power mode, **deep sleep** |
| `bleTask` (main.cpp:886) | 1 | 5 | 4 K | STATUS_UPDATE раз в 10 с, LED, OLED, таймаут файлового RX, выгрузка принятого файла в телефон |
| `beaconTask` (beacon.cpp:171) | 1 | 2 | 4 K | Запрос GPS у телефона → beacon раз в N минут (длинная преамбула) |
| `fileSendTask` (main.cpp:1046) | 1 | 3 | 8 K | File Transfer v2: чанки из RAM по LoRa, ожидание ACK/NACK, 3 раунда досылки |
| `loop()` (main.cpp:337) | 1 | 1 | 16 K | Кнопка USER, OLED-таймаут, `callTick()` |
| NimBLE host | 0 | — | — | Стек BLE; **колбэк `handleBleData` выполняется в его контексте** |

Режим ретранслятора — отдельная ветка: `repeaterTask` (ядро 0) + `wifiMonitorTask` + `beaconTask`,
`loraTask` не создаётся, deep sleep не применяется.

### 1.3 Слои

**Радио** (`lora_radio.*`): RadioLib SX1262, 23 канала 863.15 + n×0.3 МГц, SF7/BW250/CR 4/7,
sync 0x34, CRC вкл. Три power mode: `CONTINUOUS_RX`, `DUTY_CYCLE_RX` (RadioLib
`startReceiveDutyCycleAuto`), `SLEEP` (фактически standby). Преамбула 8 обычная / 32 «будящая»
(`loraSendWake`). На V4 дополнительно GC1109 PA (пины 7/2/46, +6 дБ).

**Пакеты** (`packet.h`): AUDIO 0xA0 (39 Б, Codec2 3200 — 4×8 Б), TEXT 0xB0 / TEXT_ACK 0xB1,
FILE_START 0xC0 / CHUNK 0xC1 (120 Б данных) / ACK-NACK 0xC2 / END 0xC3, BEACON 0xD0 (36 Б, CRC16),
CALL_* 0xE0-0xE6. Адресация — последние 2 байта MAC (`dest`), 0x0000 = broadcast; для звонков и
peer-ID используются 4 байта MAC.

**BLE** (`ble_service.*`): Nordic UART Service, TX-notify + RX-write-NR, MTU 128, без BLE-security;
авторизация — 4-значный PIN из MAC, проверяется командой 0x25/0x26 на уровне приложения.
Команд — 45 (0x01…0x32).

**Приложения**: голос (PTT/VOX, wake-пакет с длинной преамбулой), текст (дедуп 16 записей/30 с,
ACK для адресных), файлы v2 (загрузка в RAM ESP32 → автономная отправка с NACK-досылкой,
bitmap пропусков), beacon/peers, звонки (ALL/PRIVATE/GROUP/SOS + accept/reject/cancel),
ретранслятор (store & forward + WiFi-монитор), OLED, батарея (ADC ×5.55).

### 1.4 Android

| Компонент | Роль |
|-----------|------|
| `MeshTRXService` (1311 стр.) | Foreground service, вся логика: BLE-колбэки, разбор 45 команд, реконнект, peers, сообщения, файлы, звонки, GPS |
| `BleManager` (302 стр.) | GATT: scan по service UUID, `connectGatt(autoConnect=false)`, MTU 128, notify, write NO_RESPONSE |
| `AudioEngine` | AudioRecord 8 кГц → Codec2 3200 (JNI) → 4 фрейма/пакет (80 мс), AudioTrack на приём, VOX RMS |
| `ServiceState` | LiveData-хранилище состояния для всех фрагментов |
| UI | 5 вкладок: Voice / Messages / Files / Map / Settings + IncomingCallActivity |

Поток PTT: кнопка → `sendPttStart` → запись 640 сэмплов → Codec2 → `CMD_AUDIO_TX` (33 Б)
каждые ~80 мс → ESP32 кладёт в очередь → `loraTask` шлёт 39-байтный LoRa-пакет.

## 2. Реестр дефектов

### P0 — ломают связь прямо сейчас

**P0-1. Цикл deep sleep вместо энергосбережения** — `main.cpp:189-213, 425-470`
Любая потеря BLE (в т.ч. кратковременная) → безусловный `enterDeepSleep()` без grace-периода.
Пробуждение = reset. Окно на реконнект 3 с. Итог — вечный цикл ребутов.

**P0-2. Android сдаётся навсегда после 10 попыток** — `MeshTRXService.kt:198-217`
`maxReconnectAttempts = 10`, максимальная пауза 10 с → примерно за 1,5 минуты попытки
исчерпываются, дальше нужен ручной вход в приложение. `autoConnect()` вызывается только из
`onResume` MainActivity (`MainActivity.kt:42,178`).

**P0-3. Медленное обнаружение устройства** — `ble_service.cpp:87-88`
Advertising interval 1000-2000 мс + `enableScanResponse(false)`. Для окна в 3 с это почти
гарантированный промах; даже при штатной работе реконнект занимает секунды.

**P0-4. LoRa-передача внутри BLE-колбэка** — `main.cpp:1206-1450` (`handleBleData`)
`PTT_START`, `SEND_MESSAGE`, `FILE_*` вызывают `loraSend()`/`loraSendWake()` — блокирующие
(mutex до 1000 мс + ожидание TX до 500 мс), плюс `vTaskDelay(50)` в цикле чанков и
`oledShowMessage()` с `delay(100)` в `oledWake()`. Всё это выполняется в контексте хост-задачи
NimBLE → пропуск BLE-событий, таймауты, разрывы соединения.

**P0-5. Гонки за SPI радио** — `lora_radio.cpp:168,172,182,210-222,266-272`
`loraSetPowerMode()`, `loraSendWake()` (`setPreambleLength`), `getRSSI/getSNR`, `setChannel`,
`setOutputPower` работают с SX1262 **без mutex**, при том что вызываются из loraTask (ядро 0),
beaconTask, fileSendTask и BLE-колбэка (ядро 1). Это кандидат №1 на «зависшее радио», порчу
состояния чипа и на неразгаданный баг №35 (ACK не доходит).

**P0-6. Гонки за BLE notify** — `ble_service.cpp:113-118`
`bleSendNotify()` = `setValue()` + `notify()` без mutex, вызывается из loraTask, bleTask,
beaconTask, callManager и самого колбэка. Потенциально — перемешанные пакеты и падения в стеке.

### P1 — мешают диагностике и качеству

- **P1-1.** Нигде не логируется `esp_reset_reason()` — невозможно отличить deep sleep от паники/WDT. Нет счётчика перезагрузок.
- **P1-2.** `loop()` при отсутствии BLE спит 30 с (`main.cpp:345`) — кнопка не реагирует до 30 с.
- **P1-3.** Параметры соединения `updateConnParams(48, 80, 2, 500)` (`ble_service.cpp:20`): slave latency = 2 при потоке аудио каждые 80 мс — лишний jitter. Для голоса нужно latency 0.
- **P1-4.** `bleConnected` выставляется по факту GATT-коннекта, до проверки PIN — прошивка считает «телефон есть», хотя авторизации не было.
- **P1-5.** Выгрузка принятого файла в телефон: 100 Б каждые 100 мс (`main.cpp:963-978`) — 18 КБ идут 18 с, без flow control.
- **P1-6.** Wake cause для кнопки: код проверяет `ESP_SLEEP_WAKEUP_GPIO`, а `esp_sleep_enable_ext1_wakeup` даёт `ESP_SLEEP_WAKEUP_EXT1` (`main.cpp:428-437`) — ветка «разбудила кнопка» мертва.
- **P1-7.** Нет удержания сна во время активности: PTT/файл могут попасть в момент решения о сне.
- **P1-8.** Android: `send()` без очереди и без учёта того, что write NO_RESPONSE может быть отброшен при переполнении — при PTT возможна тихая потеря пакетов.
- **P1-9.** Дублирование протокола: старый файловый путь (0x0D/0x0E/0x29) и v2 (0x30-0x32) сосуществуют; `fileSessionId` используется и RX-, и TX-путём (`main.cpp:1391`, `1467`) — коллизия сессий.

### P2 — качество/энергия (после стабилизации)

- Serial включён всегда (`NDEBUG` не задан) — ~5 мА и лишняя нагрузка; нужен режим release.
- Прямые `Serial.print` мимо `LOG_*` в `lora_radio.cpp`, `beacon.cpp`.
- Нет task watchdog — зависшая задача не диагностируется.
- OLED `oledWake()` делает `delay(100)` + полный `u8g2.begin()` из любых контекстов.
- В `processLoRaPacket` для AUDIO нет фильтра по `dest` (все слышат всех — сейчас by design).

## 4. Система тестирования

Шесть уровней. Первые два уже есть, остальные строим.

### L0 — Native (хост, без железа) — есть, 20 тестов
`pio test -e native` — CRC16, bitmap, размеры структур. Дополнить: парсер BLE-команд,
адресация dest/broadcast, дедуп текста, расчёт чанков файла.

### L1 — Embedded (одно устройство) — есть, 28 тестов
`pio test -e test_embedded` — GPIO, OLED, батарея, heap, LoRa init/каналы/мощность, BLE init.
Дополнить: reset reason, стеки задач, mutex радио под нагрузкой.

### L2 — Serial-консоль в прошивке (новое) — фундамент для L3/L4

Команды (сборка `*_dev`, компилируются под `-DTEST_CONSOLE`):

| Команда | Ответ / действие |
|---------|------------------|
| `PING` | `EVT PONG id=7E88 ver=4.3.1 build=<git>` |
| `INFO` | uptime, reset_reason, boot_count, free heap, стеки задач, канал, мощность, power mode, ble_state |
| `CH <n>` / `PWR <n>` | сменить канал / мощность |
| `TX TEXT <dest|BCAST> <text>` | отправить текстовый пакет |
| `TX AUDIO <n> [gap_ms]` | отправить n синтетических аудиопакетов с известным seq |
| `TX FILE <bytes> <dest>` | сгенерировать псевдофайл (детерминированный паттерн) и отправить по v2 |
| `TX BEACON` | немедленный beacon |
| `TX CALL <all|priv|sos> [target]` | инициировать вызов |
| `RX STATS` | счётчики по типам, потери по seq, дубликаты, min/avg/max RSSI и SNR |
| `RX RESET` | обнулить счётчики |
| `LORA MODE <rx|duty|sleep>` | принудительный power mode |
| `BLE ADV <on|off>` / `BLE STATE` | управление рекламой, состояние + время с последнего разрыва |
| `SLEEP <off|light|deep <sec>>` | политика сна на лету |
| `CRASH` / `HANG` | намеренная паника / зависание задачи — проверка диагностики (только dev) |

Все асинхронные события — одной строкой `EVT <name> k=v …`, например:
`EVT LORA_RX type=A0 seq=12 rssi=-47 snr=9 len=39`, `EVT BLE_CONN`, `EVT BLE_DISC reason=8`,
`EVT BOOT reason=DEEPSLEEP count=57`, `EVT FILE_ACK sid=3 status=0`.

### L4 — BLE-эмулятор телефона на ПК (без Android)

На ноутбуке есть Bluetooth 5.2 (`hci0`) — этого достаточно, чтобы `bleak` играл роль телефона:
скан по service UUID, коннект, MTU, подписка на notify, PIN 0x25, весь набор команд.

### 19.08.2026 — почему связь пропадала: устройство без телефона не слышало эфир

Главная находка дня объясняет исходную жалобу («коннект пропадает и не
восстанавливается») лучше, чем всё найденное до этого.

**Устройство без подключённого телефона было глухим.** В `loraTask` стояла ветка:
нет BLE и не ретранслятор → `loraSetPowerMode(LORA_POWER_SLEEP)`, то есть радио
в standby, приём выключен полностью. Замер на стенде: 0 из 4 адресованных
сообщений принято, 0 из 5 маяков с длинной преамбулой. Для сети это значит, что
устройство, у которого телефон отвалился (сел, ушёл из зоны, закрыл приложение),
переставало существовать для остальных до момента нового BLE-подключения.
Ни вызова, ни сообщения, ни файла оно принять не могло.

Заменено на duty cycle RX: радио слушает периодически и просыпается на длинную
преамбулу. Разница в токе против полного standby — около 1 мА при 45 мА, которые
потребляет контроллер, то есть плата за связь ничтожна. После **4/4 принятых**
сообщений в том же сценарии.

**Смена режима стирала уже принятый пакет.** В обработчике приёма переключение
`duty → continuous` стояло *перед* `readData()`, а внутри переключения вызывается
`startReceive()`, который сбрасывает буфер чипа. Пакет, ради которого устройство
проснулось, терялся. Теперь пакет сначала читается и разбирается, и только потом
меняется режим.

**Первый пакет разговора теперь будящий.** Текст всегда, а первый кадр голоса
после паузы — с длинной преамбулой (`loraSendWake`). Маяки и вызовы так работали
и раньше; текст и голос — нет, поэтому спящий приёмник их не слышал.

**Голос под BLE больше не теряется.** Причина, найденная накануне (перерисовка
OLED на каждый принятый аудиопакет), подтверждена замером: было 27/30 при
интервале 80 мс, стало **30/30 на всех интервалах**, потери на BLE — ноль.

**Счётчик notify врал.** `bleNotifyFail` увеличивался и когда телефон просто не
подключён — на прогоне это давало 30 % «неудач» на пустом месте. Разделено:
`notify_noconn` (телефона нет), `notify_retry` (удалось со второй попытки),
`notify_fail` (реальная потеря). Добавлен один повтор через 20 мс — очередь
контроллера успевает разгрузиться. После правки на прогоне BLE: 195 уведомлений,
0 неудач.

**Адрес устройства печатался в одном виде, а принимался в другом.** `EVT INFO`
выводил `id` побайтово (`%02X%02X`), а `parseDest` в консоли читает строку как
16-битное значение — байты оказывались переставлены. Тест, подставивший `id` из
`INFO` в команду отправки, слал пакет по несуществующему адресу; при этом
диагностический хук печатал `EVT TEXT_RX` до проверки адресата, так что тест
показывал «принято». Теперь везде один формат — `%04X`. Тесты берут адреса из
самих устройств, а не из констант в коде.

**Новое в стенде:**

- `RADIO TIME [RESET]` — миллисекунды в standby/RX/TX/duty и число передач.
  Основа для оценки тока без амперметра.
- `DUTY ON|OFF` — принудительный duty cycle, чтобы проверять режим отдельно.
  Проверено: в duty приём работает, 6/6 пакетов, после первого — возврат
  в постоянный приём.
- `EVT FILE_RX_START` и `EVT FILE_END_RX` — видно, открылась ли сессия приёма и
  почему приёмник не отвечает на завершение.
- `power.py` — средний ток и ресурс батареи по фактическому времени в режимах.
- `soak.py` — многочасовой прогон с CSV: куча, перезагрузки, доли режимов.
- `test_ble.py` — повторное подключение теперь через скан (BlueZ забывает
  устройство после разрыва, и connect по адресу падал на 15-м цикле).

**Замеры энергии (окно 15 с, мощность −9 дБм, расчёт на 2000 мАч):**

| Сценарий | Радио | Всего | Ресурс |
|----------|-------|-------|--------|
| покой, телефона нет | 0,8 мА | 45,8 мА | 43,7 ч |
| постоянный приём | 5,3 мА | 50,3 мА | 39,8 ч |
| передача голоса 12 пак/с | 12,4 мА | 74,4 мА | 26,9 ч |
| приём голоса | 5,3 мА | 67,3 мА | 29,7 ч |

Вывод по энергии: радиочасть не при чём, всё решает контроллер. Наблюдавшиеся
10-12 часов от 2000 мАч соответствуют ~170 мА — вчетверо больше расчётных 45 мА,
так что искать нужно постоянно включённый экран, не выключенный модем или
питание платы, а не режимы LoRa. Light sleep для контроллера дал бы порядок
разницы (45 мА → 2,5 мА в покое) — это следующая задача.

**Фаззинг после правок:** 300 пакетов мусора и злонамеренных заголовков — 0 перезагрузок,
0 просадок памяти. Но обнаружилось другое: одиночный чужой `FILE_START` открывал сессию
приёма на весь таймаут (60 с), и всё это время устройство отказывало настоящим
отправителям. Теперь сессия, в которую не пришло ни одного чанка, закрывается через 15 с;
полный таймаут работает только когда передача действительно идёт.

**Память проверена отдельно:** три файла подряд (1, 2 и 4 КБ) — куча возвращается
к исходным 97 176 байт после каждого, буфер приёма освобождается и когда файл ушёл
на телефон, и когда телефона нет.

**Light sleep: подтверждено, что он не работает.** `esp_pm_configure` возвращает `0x106`
(`ESP_ERR_NOT_SUPPORTED`) — в текущих предсобранных библиотеках нет `CONFIG_PM_ENABLE`,
вопреки комментарию в `platformio.ini`. Статус теперь виден стенду (`EVT INFO … pm=…`)
и печатается в шапке `power.py`. Контроллер постоянно работает на 240 МГц, и это главный
расход: 45 мА против 2,5 мА в покое, то есть 43 часа против нескольких сотен.

Включение требует пересборки IDF с `CONFIG_PM_ENABLE=y`. Делать это вслепую опасно:
в истории проекта два отката подряд (`bb18e06` — CONFIG_PM_ENABLE ронял BLE-контроллер,
`2a1b727` — BLE падал на частоте ниже 240 МГц). Задача вынесена отдельно, после того как
восстановленная связь отстоится.

**Экран не при чём:** OLED гаснет через 30 с и снимает Vext, так что в покое его вклад
близок к нулю.

**Как измерить батарею честно.** Расчёт по режимам радио не знает тока платы, поэтому
добавлен `battery.py`: устройство работает от аккумулятора без USB, ноутбук подключается
по BLE как телефон и раз в минуту пишет напряжение в CSV, пересчитывая его в остаток
заряда и средний ток по кривой разряда Li-ion. Это и покажет, откуда берутся
наблюдавшиеся 10-12 часов вместо расчётных 40.

### 19.08.2026 — Android: две причины, по которым связь не восстанавливалась

1. **Поиск сервисов мог провалиться молча.** В `BleManager.onServicesDiscovered`
   неуспешный статус и отсутствующий сервис приводили к простому `return`. GATT при этом
   оставался открытым, характеристик не было, событие разрыва не приходило — и
   переподключение не начиналось никогда. Телефон показывал «подключено», рация молчала.
   Теперь такой исход закрывает GATT и поднимает `onDisconnected`, то есть включает
   обычный цикл переподключения. Таймаут подключения больше не снимается по факту
   установления соединения, а продлевается на 15 с до появления характеристик.
2. **Переподключение сдавалось после десяти попыток.** `maxReconnectAttempts = 10`
